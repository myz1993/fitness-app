⬡ Phase 1 · Foundations — Core Problems Every System Faces
📈 Scalability
The Problem
  • Single server handles 1K–10K req/s max
  • Traffic grows → CPU/RAM maxes out → crashes
  • One machine fails → entire system down (SPOF)
How to Estimate Scale
  • DAU × actions/day ÷ 86,400 = avg QPS
  • Peak = avg × 2–5× (traffic spikes)
  • 1M DAU, 10 req/day → ~120 QPS avg
  • Storage: records/day × bytes × retention days
Solutions
  • Vertical Scaling — bigger machine, simple but has ceiling & no redundancy
  • Horizontal Scaling — add more machines, requires stateless services
  • Stateless design — store session in Redis not in-process
  • Auto-scaling — add/remove machines based on CPU/RPS metrics
Key Numbers to Memorise
  • 1 server ≈ 10K HTTP req/s
  • MySQL write ≈ 1–5K TPS single master
  • Redis ≈ 100K+ ops/s
  • 1 day = 86,400s (use 100K for easy math)
⚖️ CAP Theorem
The Problem
  • Data stored on multiple nodes → nodes disagree
  • Network partition (split brain) always happens
  • Can't have perfect consistency AND availability simultaneously
5ms RTT
The Three Properties
  • C — every node returns the same data at the same time
  • A — every request gets a response (no timeout/error)
  • P — system works even when nodes can't communicate
  • P is mandatory in distributed systems → choose C or A
How to Choose
  • CP — bank transfers, inventory, tickets → data must be exact
  • AP — social feeds, shopping cart → stale data acceptable
  • Ask: "What's the cost of showing wrong data?" → guides choice
Estimation: Consistency Cost
  • Sync replication adds ~1–5ms per write (network RTT)
  • Async replication lag ~100ms–few seconds
  • Eventual consistency window = replication lag
Related: ACID vs BASE
  • ACID — SQL DBs · Atomic, Consistent, Isolated, Durable
  • BASE — NoSQL DBs · Basically Available, Soft state, Eventually consistent
⚡ Latency & Throughput
The Problem
  • Users feel slowness above 100ms
  • DB disk reads take 1–10ms each → bottleneck
  • High traffic → throughput saturates → queuing → more latency
Key Latency Numbers
  • L1 cache hit: ~0.5 ns
  • RAM read: ~100 ns
  • SSD read: ~100 µs
  • HDD read: ~10 ms
  • Same datacenter round trip: ~0.5 ms
  • Cross-continent: ~150 ms
How to Estimate
  • Throughput = 1 / avg_latency × concurrency
  • Bottleneck = slowest component in chain
  • Adding 3 DB calls at 10ms each → +30ms latency
  • Cache hit replaces DB call: 10ms → 0.1ms (100× faster)
Solutions
  • Cache — move reads from disk to memory
  • CDN — move data geographically closer to user
  • Async — don't block on slow operations
  • Index — O(n) table scan → O(log n) B-tree lookup
  • P99 not avg — optimise worst-case, not average case
  • Batching — trade latency for throughput (Kafka)

⬡ Phase 2 · Core Components — Tools, Trade-offs & What Problem Each Solves
🚦 Traffic Layer Solves: Scalability (single server limit) · SPOF · Geographic routing
Load Balancer
Distributes incoming requests across a pool of servers
What Problem It Solves
  • Single server can't handle all traffic → spread across N servers
  • One server crashes → LB detects via health check → reroutes
  • Enables horizontal scaling: add servers without changing clients
Algorithms & Trade-offs
  • Round Robin — simple, equal distribution, ignores server load
  • Weighted RR — strong servers get more traffic, manual config needed
  • Least Connections — smart, great for variable req duration, more overhead
  • IP Hash — same user → same server (session), but uneven if few IPs
Key Trade-off
L4 (TCP level) = faster, can't inspect HTTP content
L7 (HTTP level) = smarter routing by URL/header, slightly more overhead
✅ Gains
High availability · Horizontal scale · Zero-downtime deploy
⚠️ Cost
LB itself is a SPOF → need redundant LB pair · Adds ~1ms
API Gateway
Single entry point that handles cross-cutting concerns for all microservices
What Problem It Solves
  • 10 microservices → clients would need to know 10 addresses
  • Every service duplicating auth/rate-limit logic → unmaintainable
  • Centralise: auth, rate limiting, SSL, logging, routing in one place
Core Features & Trade-offs
  • JWT Auth — stateless validation, no DB lookup per req · but can't revoke mid-TTL
  • Rate Limiting — Token Bucket (allows burst) vs Leaky Bucket (smooth, strict)
  • Routing — URL pattern → service · enables canary deploy (5% to new version)
  • SSL Termination — decrypt at edge, plain HTTP internally → saves CPU on all services
Key Trade-off
Gateway adds a network hop (~1ms) and is a potential bottleneck → must be horizontally scaled behind a Load Balancer
✅ Gains
DRY principle · Single place to update auth logic · Full observability
⚠️ Cost
Extra latency · Gateway itself must be HA · Can become a god service
⚡ Cache Layer Solves: Latency (DB bottleneck 10ms→0.1ms) · Throughput · Geographic distance
Redis
In-memory data store — 100K+ ops/s, ~0.1ms latency
What Problem It Solves
  • DB reads take 1–10ms → cache in RAM at 0.1ms
  • Stateless server scaling → store session in Redis not local memory
  • Leaderboards, rate counters, pub/sub — all in one tool
5 Data Types & When to Use
  • String — cache any value, counter (INCR), distributed lock (SET NX)
  • Hash — cache objects, update single field without rewriting whole object
  • List — FIFO queue, recent activity feed (LPUSH/RPOP)
  • Set — deduplication, tags, mutual friends (SINTER)
  • Sorted Set ★ — leaderboard, Feed (score=timestamp), priority queue
Cache Write Strategy Trade-offs
Cache-Aside: app manages cache · simple · cold start miss
Write-Through: write DB+cache together · consistent · slow writes
Write-Back: write cache first → async DB · fast · risk data loss
✅ Gains
100× faster reads · Reduces DB load dramatically
⚠️ Cost
Data can be stale · Cache invalidation is hard · Memory is expensive
CDN
Geographically distributed cache — brings content close to users
What Problem It Solves
  • Server in Shanghai, user in New York
  • CDN edge node in New York
  • Origin server never gets hit for static content → massive cost saving
Pull vs Push Trade-off
  • Pull — edge fetches on first miss, auto-cached · simple · cold start slow
  • Push — you pre-upload to all edges · fast for known-large traffic · manual, stale risk
  • Use Pull for most content, Push for major events (product launch, live video)
What to Cache vs Not
  • ✅ Images, JS, CSS, fonts, public API responses
  • ❌ User personal data, real-time prices, auth responses
✅ Gains
Drastic latency reduction · Offloads origin traffic · DDoS protection
⚠️ Cost
Cache invalidation hard · Monthly CDN bill · Not for dynamic/personal data
Cache Invalidation
The hardest part of caching — when and how to remove stale data
What Problem It Solves
  • Data in DB changes but cache still returns old value
  • Users see stale prices, profiles, counts → trust issue
Strategies & Trade-offs
  • TTL — auto-expire after N seconds · simple · may serve stale up to TTL
  • Write-Invalidate ★ — write DB → DEL cache key · consistent · cold miss after write
  • Versioned Keys — user:v3:123 → new version = new key · no delete · old keys linger
  • Event-Driven — DB change → Kafka → cache service DEL · decoupled · complex chain
3 Failure Modes
  • Penetration — query non-existent key → always hits DB → Bloom Filter fix
  • Stampede — hot key expires → 10K req hit DB at once → Mutex Lock fix
  • Avalanche — many keys expire together → DB overwhelmed → Random TTL Jitter fix
Golden Rule
Always write DB first, then DELETE cache (not update). Deleting is safer than updating — avoids race conditions.
🔐 Security Layer Solves: Identity verification · Access control · Abuse prevention (Scalability)
JWT Authentication
Stateless identity verification — no DB lookup per request
What Problem It Solves
  • Every request needs to prove "who am I?" → can't query DB each time at scale
  • JWT carries identity in the token itself → gateway verifies with crypto, no DB
  • Downstream services get user context via headers, no repeated auth
Structure & Flow
  • Header — algorithm (HS256)
  • Payload — user_id, roles, exp timestamp
  • Signature — HMAC of header+payload → tamper-proof
  • Access Token: short TTL (15min–1h) · Refresh Token: long TTL (30 days)
✅ Gains
Stateless · Fast · Scales horizontally · No session store needed
⚠️ Cost
Can't revoke mid-TTL → need Redis blacklist for logout · Payload is base64 not encrypted
Authorization (RBAC / ABAC)
Controls what authenticated users are allowed to do
What Problem It Solves
  • Authentication = who you are · Authorization = what you can do
  • Without it: any logged-in user can delete any resource
  • Two levels: coarse (API endpoint) at Gateway · fine (row-level) at service
Models & Trade-offs
  • RBAC — User→Role→Permission · simple, easy to manage · less flexible
  • ABAC — rules on user/resource attributes · very flexible · complex to debug
  • ACL — per-resource permissions (Google Drive) · fine-grained · hard to audit at scale
  • Cache permission results in Redis with 5min TTL → avoid DB per request
✅ Use RBAC when
Clear roles exist (admin/editor/viewer). Most enterprise apps.
✅ Use ABAC when
Complex rules: "doctor can only see their own patients in working hours"
Rate Limiting
Prevents abuse and protects downstream services from overload
What Problem It Solves
  • One bad actor sends 1M req/s → takes down entire system
  • Scrapers, brute-force attacks, runaway clients
  • Protects DB and downstream services from traffic spikes
Algorithms & Trade-offs
  • Token Bucket ★ — allows burst up to bucket size · most realistic · recommended
  • Leaky Bucket — strictly smooth output · protects downstream · no burst allowed
  • Fixed Window — simple, cheap · boundary attack: 2× burst at window edge
  • Sliding Window — accurate, no boundary issue · high memory (1 record per req)
Distributed Rate Limiting
Multiple gateway nodes → must share counters via Redis · Use Lua script for atomic INCR+EXPIRE · Dimension by: user ID, IP, endpoint, tenant
✅ Returns
HTTP 429 + Retry-After header · client backs off gracefully
⚠️ Cost
Redis becomes critical dependency · Wrong limits hurt legitimate users
🗄️ Database Layer Solves: CAP trade-offs · Data persistence · Write scalability · Read scalability
SQL (MySQL / PostgreSQL)
Relational DB — structured data, strong consistency, ACID transactions
What Problem It Solves
  • Need guaranteed correctness: bank transfers, order placement, inventory
  • Complex queries with JOINs across related tables
  • Schema enforces data integrity (foreign keys, constraints)
ACID Properties
  • Atomic — all ops succeed or all roll back (no half-transfer)
  • Consistent — DB moves between valid states only
  • Isolated — concurrent txns don't interfere
  • Durable — committed data survives crashes (WAL log)
✅ Choose SQL when
Structured data · Transactions needed · Complex queries · <TB scale
⚠️ Limitation
Hard to scale writes · Schema changes expensive on large tables · Vertical scaling has ceiling
NoSQL Family
Four types — each solves a specific data problem SQL can't handle at scale
Document (MongoDB)
  • Solves: varying schema per record (product catalogue, CMS)
  • Trade-off: flexible + fast iteration vs no joins, no cross-doc transactions
Wide-Column (Cassandra)
  • Solves: massive write throughput + time-series queries (IoT, logs, tweets)
  • Trade-off: AP system (eventual consistency) · optimised for known query patterns only
Key-Value (DynamoDB / Redis)
  • Solves: ultra-low latency simple lookups (session, cart, cache)
  • Trade-off: O(1) reads/writes vs no complex queries
Graph (Neo4j)
  • Solves: multi-hop relationship queries (social graph, fraud, recommendations)
  • Trade-off: perfect for relationships vs poor for non-graph queries
Replication
Copies data to multiple nodes — solves read scalability and availability
What Problem It Solves
  • Single DB node → single point of failure, can't scale reads
  • Read replicas absorb read traffic (read:write often 10:1+)
  • Master fails → promote replica → minimise downtime
Sync vs Async Trade-off
  • Synchronous — write confirmed only when all replicas ACK · zero data loss · slow writes
  • Asynchronous ★ — write confirmed when master writes · fast · may lose few ms of data on crash
  • Most systems use async + accept tiny data loss window
  • Replication Lag — replica may be seconds behind master · stale reads possible
✅ Gains
Read scale-out · High availability · Failover in 30s–2min via Sentinel
⚠️ Cost
Async = possible stale reads · Failover has brief write downtime · Replication lag
Sharding
Splits data across multiple DB nodes — solves write scalability and storage limits
What Problem It Solves
  • Single DB can't hold 10TB of data or handle 100K writes/s
  • Split data horizontally: each shard owns a subset of rows
  • Write traffic distributed across shards → scales linearly
Strategies & Trade-offs
  • Hash Sharding ★ — shard = hash(key) % N · even distribution · range queries hit all shards
  • Range Sharding — shard by value range · range queries efficient · hot shard risk (new data)
  • Directory — lookup table maps key→shard · flexible · lookup table is bottleneck
  • Consistent Hashing — adding node only moves 1/N data · used by Cassandra, DynamoDB
Big Trade-off
Cross-shard JOINs are very expensive · Shard key choice is irreversible · Rebalancing is painful · Last resort after cache + replication
✅ Gains
Unlimited write scale · Distribute storage across cheap machines
⚠️ Cost
No cross-shard transactions · Complex operations · Hard to change shard key later
📨 Messaging & Async Layer Solves: Scalability (traffic spikes) · Latency (slow sync calls) · Service coupling
Kafka
Distributed event streaming — high throughput, replay, multi-consumer
What Problem It Solves
  • Need 1 event consumed by multiple independent services
  • Need to replay past events (audit, rebuild state, fix bugs)
  • Massive write throughput: millions of events/sec (logs, IoT, clicks)
  • Traffic buffering: absorb spikes, consumers process at own pace
Key Concepts
  • Topic — named channel (order-events, user-clicks)
  • Partition — topic split across machines → parallel writes
  • Consumer Group — each group gets all messages independently
  • Offset — consumer's position, can rewind to replay
  • Messages retained 7 days by default, not deleted on consume
✅ Choose Kafka when
High volume · Need replay · Multiple consumers · Event sourcing · Log pipeline
⚠️ Limitation
Operationally complex · Overkill for simple task queues · No per-message routing
RabbitMQ / SQS
Traditional message broker — task queues, flexible routing, low latency delivery
What Problem It Solves
  • Async task dispatch: send email, resize image, process payment callback
  • Decouple producer from consumer — producer doesn't wait for result
  • Work queue: N workers pull tasks, auto load-balanced
Key Concepts & Trade-offs
  • Messages deleted after ACK — no replay (unlike Kafka)
  • Push model — broker pushes to consumer → lower latency than Kafka pull
  • Exchange routing — Direct/Topic/Fanout → flexible message routing rules
  • Dead Letter Queue — failed messages after N retries → DLQ for inspection
  • SQS (AWS) — managed RabbitMQ equivalent, pairs with SNS for fan-out
✅ Choose RabbitMQ when
Task queues · Need routing rules · Lower volume · Simple to operate
⚠️ Limitation
No message replay · Lower throughput than Kafka · Messages gone after consume
Async Patterns
Design principles that apply regardless of which MQ you use
What Problem It Solves
  • Sync call chain: A→B→C→D fails if any step fails → user sees error
  • Async: A puts event on queue, returns immediately → resilient
  • Traffic spike: 100K req/s hits queue, consumers process at 1K/s → DB survives
Critical Reliability Concepts
  • ACK — consumer confirms processing · broker retries if no ACK · at-least-once delivery
  • Idempotency ★ — same message processed twice = same result · use message ID dedup
  • DLQ — after N failures, move to dead letter queue · prevents poison pill blocking queue
  • Backpressure — queue full → producer slows down · prevents OOM
Core Trade-off of Async
Gain: resilience, decoupling, traffic buffering
Cost: eventual consistency (result not immediate) · harder to debug · out-of-order delivery possible
